# Phase 2 chat architecture

> **Current state.** Phase 2, Milestone 1 implements a **mock-only chat
> foundation**. Every control below marked **[implemented]** is real and
> tested; everything marked **[deferred]** does not exist yet and this
> milestone does not lay groundwork that quietly enables it. Nothing here
> makes a network request, and nothing here can trigger a privileged action.
> Milestone 2 (see
> [docs/phase-2-provider-architecture.md](phase-2-provider-architecture.md))
> adds the provider registry, request/response schemas, a timeout decorator,
> and provider-status display on top of this same foundation — this document
> is kept as the record of what Milestone 1 built and is not rewritten to
> describe Milestone 2's additions.

## Message model

`src/shared/schemas/chat.schema.ts` defines `chatMessageSchema`:

| Field       | Type                                          | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`        | UUID string                                   | Generated by `crypto.randomUUID()` in the renderer's `ConversationController`, never by the schema itself — the schema only validates the shape.                                                                                                                                                                                                                                                                                                                                                  |
| `role`      | `'system' \| 'user' \| 'assistant' \| 'tool'` | `tool` is declared for forward compatibility with a later milestone's tool-call support and is never produced by anything in this milestone — the mock provider never returns one, and nothing constructs one.                                                                                                                                                                                                                                                                                    |
| `content`   | bounded string                                | 1–8,000 characters. Rejects unsafe control characters (NUL and other C0/C1 controls) while allowing tab, newline and carriage return, since chat content is legitimately multi-line — unlike the single-line `displayString` used for settings identity fields. Also rejects Unicode bidirectional override/isolate characters, the same "Trojan Source" defence `settings.schema.ts` already applies to display strings, extended here because assistant output is untrusted text a human reads. |
| `createdAt` | UTC ISO-8601, no offset                       | Supplied by the caller, exactly like every other timestamp in this codebase (`src/shared` has no clock access — see `docs/architecture.md`'s "Timestamps and clocks" section).                                                                                                                                                                                                                                                                                                                    |
| `status`    | optional `'complete' \| 'error'`              | Declared on the schema now, **unused by this milestone's actual logic** — see [Conversation state](#conversation-state) for why a failed attempt does not become an `'error'`-status message. Exists so a later milestone (for example, a streaming provider marking a message `'streaming'` while it fills in) is a new enum member, not a new field requiring a schema-version bump.                                                                                                            |
| `metadata`  | optional bounded JSON object                  | Reuses `auditParametersSchema` — the exact schema audit records already use — rather than a second implementation. Depth, breadth, size and key length are all bounded, and any field whose name looks capable of carrying a credential (`apiKey`, `token`, `secret`, …) is rejected unless its value is already `[REDACTED]`, the same redaction contract the audit log enforces. **A message can never carry a secret in its metadata**, structurally, not by convention.                       |

`chatMessageSchema` is `z.strictObject` — an unrecognised field is rejected outright, matching every other persisted or validated shape in this codebase. `createChatMessage(input)` validates and returns a message, or throws; nothing downstream ever sees an unvalidated message.

**Nothing about a message is persisted to disk in this milestone.** Conversation state lives only in renderer memory for the lifetime of the window. `CHAT_CONVERSATION_MAX_MESSAGES` (200, in `src/shared/constants.ts`) bounds memory growth, not a file format.

## Provider interface

`src/shared/chat/provider.ts` defines `ChatProvider`:

```ts
interface ChatProvider {
  readonly id: string;
  send(
    request: { readonly messages: readonly ChatMessage[] },
    options?: { readonly signal?: AbortSignal },
  ): Promise<{ readonly content: string }>;
}
```

Deliberately minimal and provider-independent:

- **No Electron dependency, no filesystem or shell access.** The type itself cannot express either — there is nothing in the interface a provider could use to reach one.
- **No network access is possible from an implementation placed under `src/shared`.** `eslint.config.js`'s purity boundary — the same rule that blocks Electron and every Node built-in throughout `src/shared` — also blocks `fetch`, `XMLHttpRequest`, `WebSocket` and `EventSource` as bare globals. A future edit that tried to add a real network call to a provider living in this directory would fail lint, not merely fail review.
- **Cancellation is a plain `AbortSignal`** — the standard, dependency-free mechanism. Nothing here starts a timer or a request that would need a bespoke cancellation channel; this is a real, exercised feature (see the mock provider's abort handling below), not a decorative type.
- **No provider implemented here is real.** The only implementation in this codebase is the deterministic mock. Adding a real provider (GLM, an OpenAI-compatible endpoint, Ollama) is explicitly out of scope for this milestone and is not designed here beyond the interface shape — in particular, _how_ a future real provider would use an API key without a plaintext key ever reaching this layer is an open question for whichever milestone adds one, not answered by this one.

## Mock provider

`src/shared/chat/mock-provider.ts`'s `createMockChatProvider()` is the only `ChatProvider` in this codebase.

- **Deterministic.** The reply is templated from the conversation alone — the latest user message, truncated to 200 characters and echoed into a fixed sentence. The same conversation always produces the same reply.
- **No network request, no secret access.** It reads nothing from settings or the secret store; its only input is the `messages` array it is handed.
- **Clearly marked.** Every reply begins with `[Mock provider]` and states plainly that no real model is connected and no network request was made.
- **Simulated latency, not randomness.** `delayMs` (default 400ms) makes the loading state actually visible in the UI; tests pass `delayMs: 0` for an instant, still-deterministic result, or use fake timers to assert the loading state mid-delay.
- **A documented, deterministic failure trigger.** Sending the exact message `/mock-fail` (`MOCK_CHAT_PROVIDER_FAILURE_TRIGGER`) makes the provider reject with a `ChatProviderError('PROVIDER_REQUEST_FAILED', …)` instead of responding. This exists so the failure and retry UI can be exercised — by tests and during manual review — without needing a real, flaky failure to occur.
- **Injectable.** Tests construct their own `ChatProvider` implementations (see `tests/unit/renderer/conversation-controller.test.ts`) to control exactly when and how a response resolves, independent of the mock's own timing.

## Conversation state

`src/renderer/chat/conversation-controller.ts`'s `ConversationController` is **framework-independent** — no React import, no DOM dependency beyond standard globals (`crypto.randomUUID`, `AbortController`, `setTimeout`) available in both a browser and Vitest's `node` test environment. This mirrors the pure-core-behind-a-thin-adapter split already used elsewhere in this codebase (`decidePermission`, `main/settings-service.ts`), and it is what makes every conversation behaviour unit-testable with plain Vitest — no React Testing Library, no jsdom, neither of which is part of this project's toolchain (see `docs/security-model.md`, known limitation 18).

`useConversation.ts` is the thin React binding: it owns no logic, only a `useState`/`useEffect` subscription to the controller.

**State shape:**

```ts
interface ConversationState {
  readonly messages: readonly ChatMessage[];
  readonly status: 'idle' | 'awaiting-response';
  readonly error: { readonly message: string } | null;
}
```

**The message list is append-only.** Once added, a message is never mutated or removed — on success, on failure, or on retry. Loading and error state live _outside_ the message array entirely, which is the design decision behind `ChatMessage.status` going unused in this milestone: a failed attempt never becomes an `'error'`-status message sitting in the transcript. Instead:

- **Submit** trims the input, validates it through `createChatMessage`, appends the user message, sets `status: 'awaiting-response'`, and calls the provider. A no-op for a blank message, and a no-op while a response is already pending — the duplicate-submission guard.
- **On success**, the assistant's reply is validated through the same `createChatMessage` and appended; `status` returns to `'idle'`.
- **On failure** (a thrown `ChatProviderError` or any other exception), **no assistant message is added.** The user's message stays exactly where it was; `status` returns to `'idle'`; `error` is set to a generic, safe message. A raw `Error.message` from an unknown exception is never forwarded — an assistant reply is untrusted output, and symmetrically, so is whatever a provider implementation throws.
- **Retry** re-sends the existing conversation without adding a second copy of the last user message, and is a no-op unless idle with a standing error.
- **A conversation at `CHAT_CONVERSATION_MAX_MESSAGES`** refuses further submission with an explanatory error, without contacting the provider.
- **Cancellation.** Each request gets its own `AbortController`; `dispose()` (called from `useConversation`'s unmount cleanup) aborts any in-flight request and stops delivering further state updates — the same purpose the `cancelled` boolean flag already serves around `App.tsx`'s async effects, backed here by a real signal since `ChatProvider.send` accepts one.

## UI

`src/renderer/chat/Chat.tsx`, mounted from `App.tsx`'s `'ready'` phase, replacing the previous static welcome screen with the assistant's name and status line as a compact header above the chat surface.

- **Empty state** — a friendly prompt when no messages exist yet. (Milestone 2 moved the "which provider is actually answering" text out of this prompt and into its own status line — see `docs/phase-2-provider-architecture.md`.)
- **Message list** (`role="log"`, `aria-live="polite"`) — each message a bubble labelled by role.
- **Loading state** — an `aria-live` "…is thinking" line while `status === 'awaiting-response'`; the composer is disabled for the same duration, which is the actual duplicate-submission prevention the user sees (the controller enforces it structurally regardless).
- **Error state** (`role="alert"`) with a **Retry** button, shown only when `state.error` is set.
- **Composer** — a `<textarea>` (multi-line, since content allows `\n`) with a visible `<label>`, Enter to send, Shift+Enter for a newline (via the textarea's owning `<form>`'s native `requestSubmit()`, not a hand-built event), and a submit button whose label changes while sending.

**No unsafe HTML rendering.** `message.content` is rendered as a plain JSX text child — React escapes every string child by default, so no provider response, however hostile, can inject markup or execute a script. `dangerouslySetInnerHTML` appears nowhere in this milestone. Multi-line content is preserved visually with CSS `white-space: pre-wrap`, not by converting `\n` into `<br>` markup. **Markdown rendering does not exist in this milestone** — the simplest way to satisfy "never render Markdown as executable HTML unless safely sanitized and explicitly justified" is to not render Markdown at all yet, which sidesteps needing a sanitizer dependency or a justification for one.

## Security boundary

- **No new IPC channel.** `src/preload/index.ts` is unmodified; the bridge still exposes exactly `health`, `settings.{get,update}` and `secrets.{status,write,clear}`, asserted by the unmodified end-to-end bridge-shape test. Chat never calls `window.localAgent` at all.
- **No privileged action can be triggered by chat text.** There is no code path from a chat message — typed by the user or returned by a provider — to `main/executor.ts`, to `handleActionProposal`, or to any Electron or Node API. The entire chat feature runs inside the sandboxed, unprivileged renderer and the pure `src/shared` layer.
- **No model output is treated as authorization for anything.** This is not a policy chat honours; it is a structural absence — there is no mechanism anywhere in this milestone by which text returned from a `ChatProvider` could reach the permission engine, the executor, or any action proposal.
- **No secret reaches chat state.** The mock provider never imports `main/secrets.ts` (it cannot — it is not privileged code and has no path to it), never reads settings, and `chatMessageMetadataSchema` structurally rejects a secret-looking metadata field unless its value is already redacted.
- **No network request is possible**, not merely absent by inspection: `src/shared/chat/*`'s network-capable globals are blocked by the same ESLint rule that has protected `src/shared` since Milestone 1. `tests/unit/shared/mock-provider.test.ts` additionally spies on `globalThis.fetch` at runtime and asserts it is never called, across a success and a failure.
- **Every Phase 1 security boundary is unmodified.** `main/*`, `src/preload/index.ts`, `eslint.config.js`, the permission engine, the audit log, and the emergency-stop runtime have zero diff in this milestone. `tests/e2e/electron-smoke.test.ts` still passes unmodified, confirming the sandbox, the CSP, and the exact bridge shape all hold.

## Testing

| Area                                                                                                                                                                                                                 | File                                                  |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Message schema validation (roles, bounds, control characters, bidi, metadata redaction, unknown fields)                                                                                                              | `tests/unit/shared/chat.schema.test.ts`               |
| Mock provider (determinism, marking, echo/truncation, delay, the failure trigger, abort, no `fetch` call)                                                                                                            | `tests/unit/shared/mock-provider.test.ts`             |
| Conversation behaviour (submit, loading, success, failure preserving prior state, retry without duplication, duplicate-submission prevention, oversized-message rejection, conversation-length bound, dispose/abort) | `tests/unit/renderer/conversation-controller.test.ts` |

**No component-level render test exists for `Chat.tsx`**, for the same reason `Onboarding.tsx` and `App.tsx` have none (`docs/security-model.md`, known limitation 18): React Testing Library and jsdom are not part of this project's toolchain, and this milestone did not add them. This gap is substantially narrower than it would otherwise be, because every behaviour that matters — state transitions, validation, error handling, HTML-safety of stored content — is implemented in the framework-independent `ConversationController` and is fully covered there. What remains untested by an automated test is purely the JSX rendering and event wiring in `Chat.tsx` itself (for example, whether a click actually reaches `retry()`).

## What remains deferred

Everything in the Phase 2, Milestone 1 task's "Do not implement" list remains genuinely absent, not merely unused:

- Real cloud model calls; real Ollama, GLM, or OpenAI-compatible requests
- API-key retrieval for a provider call
- New privileged tools, filesystem access, shell execution, browser automation
- Email, camera, microphone, voice
- Autonomous actions, background agents, multi-agent runtime
- Vector memory or RAG
- Plugin marketplace, cloud sync, telemetry
- Any action execution from model output

A later Phase 2 milestone that adds a real provider, a tool, or persistence for conversation history is expected to extend this design (the `ChatProvider` interface, the message schema's `tool` role and `metadata` field) rather than replace it — but doing so is out of scope here and not started.
